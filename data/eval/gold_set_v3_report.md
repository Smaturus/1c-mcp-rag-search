# Hold-out v3: состав, baseline и ограничения

**Дата:** 2026-10-23 · **Источник запросов:** `set2.txt` (100 запросов, 23 домена)
· **Статус:** независимый hold-out, **не использовался для настройки**.

Задача набора — честно проверить retrieval и роутер на запросах, которые не
участвовали в разработке. v2 использовался для настройки, v3 — финальная
проверка перед решением по ADR 0009. После открытия hold-out его нельзя
использовать для тюнинга: для следующей итерации нужен новый набор.

## Файлы

| Файл | Назначение |
|---|---|
| `data/eval/gold_set_v3_holdout.jsonl` | 100 размеченных запросов (file-level relevant_sources) |
| `data/eval/anchors_v3.jsonl` | 10 коротких лексических якорей для регрессии точного поиска |
| `scripts/validate_goldset_v3.py` | проверка схемы, путей и инвариантов набора и якорей |

| `scripts/eval_router_v3.py` | точность роутера на v3 |
| `data/eval/gold_set_v3_report.md` | этот отчёт |

## Схема строки

`id`, `category`, `query`, `relevant_sources` (реальные file-level пути корпуса),
`scope` (`code` / `metadata` / `none`), `answerable`, `confidence`
(`high` / `medium` / `low`), `expected_route` (`lexical` / `vector` / `hybrid`),
`type` (`exact` / `semantic` / `trap`), `primary_source`, `finetune_ready`, `notes`.

### Правила маршрутов и типов (ADR 0006)

- запросы с точными именами/процедурами (№2, 8, 14, 21, 48, 53, 59, 74, 80, 92)
  → `lexical` + `exact`;
- диагностика без точных имён (№3, 10, 17, 33, 39, 52, 64, 67, 73, 75, 87, 91, 97)
  → `semantic` + `vector`;
- сочетание точного имени и диагностики (26 запросов) → `trap` + `hybrid`
  (fallback-сценарий).

Отклонения маршрута от исходной таблицы set2 — 3:

| id | set2 | в v3 | Причина |
|---|---|---|---|
| 25 | vector | hybrid/trap | точный объект + диагностика → fallback |
| 48 | hybrid | lexical/exact | «выбор счёта в документе» — точный модуль, а не смысловой поиск |
| 49 | vector | hybrid/trap | точный документ + «как исправить» → fallback |

## Что показала сверка с корпусом

Разметка делалась по реальному корпусу (`data/chroma_xml`), а не по общим
представлениям о конфигурации. В публичной версии платформенное имя продукта
заменено нейтральным «конфигурация»; смысл запросов и разметка не менялись.
Часть объектов set2 в этой выгрузке отсутствует или представлена только
XML-метаданными:

- **нет BSL-объекта**: «Заказ на производство» (есть «Задание на производство» —
  другой объект), «Начисление зарплаты», «Расчёты между головной и филиалами»,
  давальческое сырьё, регистр возвратной тары, «Конвертация данных 2», COM,
  хранилище конфигурации, регламентированные декларации;
- **только XML-метаданные**: справочник «ДолжностиОрганизаций», регистр
  «Технологические карты спецификаций планирования», подсистема «РасчётЗарплаты»,
  шаблон «РеестрДокументов», отчёт «ВедомостьПоВзаиморасчетам…_ДопПоказатели».
  Эти 5 запросов получили `scope=metadata`;
- 24 запроса помечены `answerable=false` и **исключаются из nDCG** (иначе любая
  система получает несправедливые нули). Их список — в `notes` каждой строки.

## Finetune-ready (12)

Запросы с одним чётким целевым модулем (pair query → chunk); использовать только
для дообучения, не для оценки: №7, 32, 46, 47, 50, 53, 59, 83, 85, 88, 92, 97.
Остальные запросы имеют 2–3 источника или низкую уверенность — для пар
«запрос → чанк» без ручной верификации не годятся.

## Baseline (3 прогона)

**Retrieval, 71 code-запрос** (3 независимых прогона, k=10, mean ± std):

| Режим | Hit@1 | MRR@10 | nDCG@10 | Recall@10 |
|---|---|---|---|---|
| `lexical` (BM25) | 0.070 | 0.107 | 0.116 | 0.181 |
| `vector` | 0.085 ± 0.024 | 0.200 ± 0.016 | **0.205 ± 0.014** | 0.319 ± 0.022 |
| `pearson` | 0.066 ± 0.008 | 0.193 ± 0.009 | 0.197 ± 0.007 | 0.313 ± 0.009 |
| `hybrid` | 0.056 ± 0.014 | 0.165 ± 0.009 | 0.183 ± 0.005 | 0.295 ± 0.012 |

Парный тест vector vs hybrid (per-query средние по 3 прогонам): Δ = **+0.0226**
nDCG@10, bootstrap 95 % CI **[−0.0191; +0.0614]**, paired t-test p = **0.275**,
bootstrap p = 0.268 — **не значимо**. Абсолютные значения ниже, чем на v2
(0.339), потому что набор новый и заметно сложнее; это ожидаемо для честного
hold-out. Lexical nDCG@10 = 0.116 — ниже порога 0.34, который фигурирует в
условиях принятия ADR 0009.

**Metadata, 5 запросов** (3 прогона): `vector` nDCG@10 0.600;
`hybrid` 0.435 ± 0.015; `lexical` 0.000 (индикативно, n=5).

Отчёты baseline: [`v3_code/report_stability.md`](v3_code/report_stability.md),
[`v3_code/report_paired.md`](v3_code/report_paired.md),
[`v3_router.md`](v3_router.md), metadata — [`v3_metadata/report_stability.md`](v3_metadata/report_stability.md).

**Metadata, 5 запросов** (3 прогона): `vector` nDCG@10 0.600;
`hybrid` 0.435 ± 0.015; `lexical` 0.000 (индикативно, n=5).

**Роутер, 100 запросов:** accuracy **58/100 (58 %)**, на 76 отвечаемых 43/76.
По ожидаемому маршруту: lexical 12/35 (34 %), vector 22/30 (73 %), hybrid 24/35 (69 %).
Главная ошибка — `lexical → hybrid` (21 случай): правила ждут CamelCase/код, а
естественные имена в кавычках уходят в безопасный hybrid. Это разрыв контракта,
а не повод менять разметку под роутер; исправления проверять на dev-наборе,
а не на v3.

## Решение по ADR 0009 (2026-10-23)

Условия `accepted` проверены на v3 (все должны выполняться одновременно):

| Условие | Результат |
|---|---|
| paired p < 0.05 и CI не пересекает 0 на v3 | **FAIL**: Δ +0.0226, CI [−0.0191; +0.0614], p = 0.275 |
| max/chunk-level не схлопывает отрыв | **не проверено** — условие не подтверждено |
| ablation подтверждает вклад нарезки | **PASS**: разрыв +0.078 на одной выгрузке (`ablation_2x2.md`) |
| per-file BM25 ≥ 0.34 | **FAIL**: lexical nDCG@10 = 0.116 |
| хотя бы одна гипотеза подтверждена/опровергнута | **PASS**: vector-направление повторено, но не значимо; найден разрыв роутера `lexical→hybrid` |

**Решение:** ADR 0009 остаётся **proposed**, дефолт `MCP_1C_SEARCH_MODE=hybrid`
не меняется. Обоснование отказа: на независимом наборе преимущество vector
статистически не значимо (p = 0.275, CI включает 0), а per-file BM25 ниже
порога; условие accepted не выполнено. Что проверено и чего не хватает —
зафиксировано в ADR 0009 и `data/eval/v3_report.md`.

## Воспроизведение

```powershell
python scripts/validate_goldset_v3.py
python scripts/eval_anchors.py
python scripts/eval_router_v3.py
python scripts/eval_router_v3.py --answerable-only

$env:MCP_1C_CHROMA_DIR="data\chroma_xml"
$env:MCP_1C_BM25_DIR="data\bm25_all"
python scripts/eval_pipeline.py --golden data\eval\gold_set_v3_holdout.jsonl `
  --scope code --answerable-only --chroma-dir data\chroma_xml `
  --collection code_proc --modes lexical,vector,pearson,hybrid --out-dir data\eval\v3_code
python scripts/eval_paired.py --runs-glob "data\eval\v3_code\run_*.json" --a vector --b hybrid
```

Chroma требует записи при открытии; в песочнице использовалась копия
`chroma.sqlite3` (оригинал не изменялся).

## Ограничения и политика

1. Разметка file-level сделана по корпусу; 17 отвечаемых запросов имеют
   confidence=low и требуют ручной проверки до принятия решения.
2. 24 запроса вне корпуса нельзя считать промахами retrieval — они исключены из
   nDCG и могут использоваться только для проверки отказа/маршрутизации.
3. Metadata-scope — всего 5 запросов; выводы по нему индикативны.
4. Retrieval-базовый уровень снят по 3 прогонам; для `accepted` по ADR 0009
   нужен более сильный эффект (p < 0.05, CI без 0) или существенно больше запросов.
5. **v3 нельзя использовать для настройки.** После фиксации baseline — только
   чтение; для следующей итерации собирается новый hold-out.
