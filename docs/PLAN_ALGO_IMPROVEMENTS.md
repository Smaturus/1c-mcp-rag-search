## 0. Ограничения и инварианты

1. Не трогать `data/chroma_xml`, `data/chroma_xml_eval`, `data/bm25_all`, `data/chroma_e5_base`, `data/bm25_e5_base` — только чтение.
2. Новые индексы/прогоны — только в новые каталоги:
   - `data/bm25_code_proc_live/`
   - `data/metadata_xml_v2/` (если дойдёт до фазы E)
   - `data/eval/_runs_algo/`
   - заметки — `data/local_notes/after_e5_base/`
3. Живой MCP (`cordis.patch.yml`) не менять до прохождения фазовых гейтов; каждое переключение — отдельное «да».
4. Метрики: nDCG@10 — ворота; hit@1/MRR@10/recall@10 — отчёт; latency — ворота ≤3×.
5. Оценка: `run_eval_runs.py` (4/3/4 прогона), `eval_report_pair.py` (paired bootstrap 95 %, p), `record_control_delta.py` для δ; сравнение только на одинаковых gold SHA.
6. Кодовые изменения (`src/`, `scripts/`) — только после «да» на конкретную фазу, с diff до применения и pytest после.

## 1. Фаза A — baseline и harness (без изменений логики)

**Цель:** зафиксировать текущий live-baseline и получить воспроизводимый способ сравнивать варианты.

1. Прогнать текущий live-конфиг (`chroma_xml` + `bm25_all` + e5-small, hybrid) в `data/eval/_runs_algo/baseline_*` (4/3/4), записать `baseline.md`.
2. Проверить SHA gold и counts/fingerprint индексов (sqlite RO).
3. Добавить лёгкий notes-скрипт `data/local_notes/after_e5_base/compare_runs.py`:
   - принимает два набора прогонов (old/new) и метрику;
   - печатает mean/Δ/CI/p/W-T-L (через существующий `eval_report_pair`), не меняя его.
4. Гейт A: baseline воспроизводит live-числа (± шум), иначе стоп.

**Ручная работа:** нет. **Время:** 30–60 мин.

## 2. Фаза B — BM25 только по code (наибольший ожидаемый эффект без ML)

**Гипотеза:** `bm25_all` включает 25 026 metadata-карточек; IDF/длины документов смешаны, из-за чего hybrid на code-запросах теряет точность. Отдельный BM25 по `code_proc` должен улучшить exact/lexical-часть.

1. Собрать индекс (read-only исходник):
   ```text
   py scripts/build_bm25.py --chroma-dir data/chroma_xml \
     --out data/bm25_code_proc_live --id-prefix bsl_proc:
   ```
2. Гейты индекса: `n_docs=154560`, id-множество = `code_proc` из sqlite RO; пустых 0; размер записать.
3. Сравнительные прогоны (только code-запросы, hybrid):
   - baseline: `MCP_1C_BM25_DIR=data/bm25_all`;
   - candidate: `MCP_1C_BM25_DIR=data/bm25_code_proc_live`;
   - `run_eval_runs.py` ×2 на v2/v3/v4, `--modes vector,hybrid`;
   - paired-сравнение hybrid candidate vs hybrid baseline (`eval_report_pair.py`).
4. Гейт B (принять эксперимент): на v3 и v4 нет регрессии > δ, на v2/holdout есть улучшение по nDCG/recall или exact-подгруппе; latency не хуже 3×.
5. Только после PASS — **кодовая фаза B2**: поддержка двух BM25-индексов (code/metadata) в `config.py`/`search_modes.py` (или отдельный code-tool), затем live-смоук и, при согласии, переключение контейнера MCP.

**Ручная работа:** нет; только интерпретация результата. **Время:** индекс ~1–2 мин; прогоны ~15–20 мин; код B2 — 0,5–1 день.

## 3. Фаза C — диверсификация выдачи (per-source cap / MMR)

**Гипотеза:** несколько чанков одного файла вытесняют другие релевантные файлы; для агента важнее покрытие источников.

1. Реализовать в коде (за флагом, не ломая текущие метрики) пост-обработку top-k:
   - `max_per_source` (например, 2) и/или MMR по `source`;
   - применять в `format_candidates`/`search`-слое, конфигурируемо.
2. Метрики автоматически:
   - nDCG@10/hit/recall (как раньше; при source-level дедупе ADR 0004 может не измениться);
   - новые: `unique_sources@10`, `source_coverage` (доля разных `source`), `duplicates@10`.
3. Гейт C: `unique_sources@10` растёт, nDCG не падает > δ, latency ≤3×; live-смоук выдачи.
4. Принять/оставить флаг по результатам; без ручной разметки.

**Ручная работа:** нет. **Время:** 0,5–1 день.

## 4. Фаза D — identifier-aware query expansion (полностью автоматическая)

**Гипотеза:** exact-name запросы (`ЗаполнитьРазделАвансы`, `НДСсАвансов`) теряются, потому что запрос и документ токенизируются по-разному; расширение запроса токенами идентификатора и синонимами из metadata помогает exact-подгруппе.

1. Автоматически построить alias-словарь из уже извлечённых metadata (`parse_config_xml.py` / `metadata_xml`):
   - имена объектов/процедур, синонимы, представления;
   - разбиение camelCase/snake_case;
   - без ручного курирования.
2. Встроить в поиск (за флагом): расширение только BM25-запроса (vector не трогать), нормализация/транслитерация — по необходимости.
3. Оценка: v2/v3/v4 + отдельный срез `type=exact` (автоматически из gold); сравнение paired.
4. Гейт D: exact nDCG/hit растёт значимо, общий nDCG не падает >δ; на holdout нет регрессии; latency ≤3×.
5. Риск: расширение добавляет шум — обязательно проверять на holdout, не только dev.

**Ручная работа:** нет (словарь генерируется из корпуса/metadata). **Время:** 1–2 дня + прогоны.

## 5. Фаза E — расширение metadata-извлечения (алгоритмически, но с оговоркой)

**Гипотеза:** metadata-карточки можно обогатить полями, которые уже есть в XML (синонимы, иерархия, реквизиты, табличные части), и это улучшит metadata-поиск и подсказки.

1. Расширить `parse_config_xml.py` (или отдельный builder): автоматически извлекать дополнительные поля; собрать **новую** коллекцию `metadata_xml_v2` (не трогая текущую `metadata_xml`).
2. Автоматические структурные гейты: число карточек, отсутствие пустых, покрытие типов, размер; smoke-поиск.
3. Ограничение: metadata-gold всего 5 запросов — статистически недостаточно. Поэтому фаза E сначала **структурная** (не продуктовая): оцениваем покрытие/полноту, а качество — только после расширения metadata-gold (это уже ручная разметка, отдельное решение).
4. Не менять live-metadata, пока нет отдельного плана и gold.

**Ручная работа:** для структурной части — нет; для оценки качества — да (нужна разметка). **Время:** 1–2 дня.

## 6. Фаза F — RRF/hybrid-параметры (дешёвый автоматический sweep)

1. Grid search по `RRF_K` (например 20/40/60/80/100) и `HYBRID_TOP_K` (30/50/80) на dev-v2.
2. Лучший по dev вариант проверить на v3/v4 (holdout), paired CI.
3. Гейт F: улучшение на dev и отсутствие регрессии на holdout; иначе оставить текущие k=60/top=50.
4. Изменение — только через env/config, с записью в ADR.

**Ручная работа:** нет. **Время:** несколько часов прогонов.

## 7. Фаза G — регрессионный harness (инфраструктура)

1. Notes-скрипт `eval_regression.py`: быстрый набор (10 anchors + 20–30 фиксированных запросов), порог nDCG, вывод JSON.
2. Опционально — ночной запуск (не в PR-CI, т.к. индексы локальные).
3. Гейт G: любой будущий PR/изменение прогоняется через harness; регрессия >δ — стоп.

**Ручная работа:** нет. **Время:** 1 день.

## 9. Definition of Done (для каждой фазы)

1. Изменение за флагом/в новом индексе; live не тронут до отдельного решения.
2. Прогоны в `data/eval/_runs_algo/`; отчёт `data/local_notes/after_e5_base/algo_<phase>.md`.
3. Пары old/new с CI и p; вывод «принять/отклонить/неразличимо».
4. Индексы/счетчики/священные пути без изменений; новые каталоги только в разрешённых путях.
5. pytest/ruff — зелёные; diff кода показан до применения.
6. Для live-изменения — отдельное «да», backup yml, смоук (rrf-поля, codesearch/metadatasearch), rollback.

## 10. Вне объёма

- Переход на e5-base/e5-large, fine-tuning, reranker по умолчанию.
- Ручная разметка новых gold-set (только после отдельного решения).
- Пересборка векторных индексов без eval-гейта.
- Изменение `bm25_all`/`chroma_xml`/`chroma_e5_base`.
- Правки `docs/PLAN_AFTER_E5_BASE.md` и закрытых планов.
