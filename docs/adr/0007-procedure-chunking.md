# ADR 0007: Chunking BSL по процедурам

- **Статус:** принято
- **Дата:** 2026-10-22
- **Контекст:** измеренная проблема — **32,1 % чанков (39 882 из 124 253)
  длиннее лимита e5 в 512 токенов**; у коллекции `metadata` это 78 % чанков.
  Хвост таких чанков не участвует в эмбеддинге. Дополнительно: символьное окно
  в 1200 символов режет логику посередине, а BSL имеет естественную единицу —
  процедуру/функцию с именем и границами.

## Решение

Нарезать `.bsl` по границам `Процедура`/`Функция` … `КонецПроцедуры`/`КонецФункции`
(модуль `src/mcp_1c_rag/chunking_procedures.py`), с правилами:

1. В текст каждого чанка добавляется строка `// file: <path> · proc: <name>` —
   усиливает точные имена (BM25) и даёт эмбеддингу контекст файла и процедуры.
2. Код вне процедур (заголовок модуля, директивы компиляции) — отдельный чанк
   `kind="module"`; директивы `&НаКлиенте` приклеиваются к следующей процедуре.
3. Длинная процедура режется на части `part k/m` с перекрытием 150 символов.
4. Модуль без процедур — fallback на символьное окно.
5. Параметры: `max_chars=1000`, `overlap=150`, это укладывает p99 в 472 токена.

Индексация — **в отдельную коллекцию** `code_proc` и отдельную базу
`data/chroma_proc`; текущие `code`/`metadata` не трогаются, чтобы сравнение
было честным, а работающий MCP-сервер не зависел от эксперимента.
Скрипт: `scripts/build_procedure_index.py` (чекпоинт, возобновление, `--no-lock`
для отдельной базы).

## Обоснование

### Техническое

1. Устраняется потеря 32 % текста при эмбеддинге — дефект, измеренный на полном
   индексе, а не гипотетический.
2. Чанк = одна процедура: логика не разрывается, метрики file-level не страдают
   от «соседних» кусков.
3. Путь и имя процедуры в тексте — прямой сигнал для точных запросов
   (`ПередЗаписью`, `ПечатьЭтикеток`) и для лексического маршрута (ADR 0006).
4. Отдельная коллекция позволяет сравнить два чанкинга на одном gold-set v2 и
   откатиться без потерь.

### Управленческое

1. **Управляемый риск:** эксперимент не затрагивает работающий индекс, откат =
   не использовать новую коллекцию.
2. **Прозрачность:** зафиксированы параметры, гейты и цифры смоука до запуска
   полной сборки — решение принималось по данным, а не по интуиции.
3. **Экономика:** переиндексация идёт локально ночью, без облачных затрат;
   срок известен из ETA в логе.
4. **Передача:** модуль, тесты и скрипт сборки самодостаточны — команда может
   повторить или откатить без автора.

## Последствия

- Новая коллекция `code_proc` (~150–200 тыс. чанков, уточняется по логу).
- Следующий шаг после сборки: `scripts/eval_chunking.py` — сравнение
  `code` vs `code_proc` на gold-set v2 (vector и hybrid), обновление ADR
  фактическими числами, затем решение о смене дефолта.
- BM25 для новой коллекции собирается отдельно (`--id-prefix bsl_proc:`) в
  `data/bm25_code_proc`, чтобы не менять глобальный индекс текущей базы.
- Попутно выявлено: метаданные (78 % сверх лимита) требуют отдельного
  уменьшения окна — кандидат на следующий шаг (ADR 0007, п. «дальше»).
