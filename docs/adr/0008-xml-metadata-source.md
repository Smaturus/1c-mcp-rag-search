# ADR 0008: Метаданные из XML-выгрузки конфигурации

- **Статус:** принято
- **Дата:** 2026-10-22
- **Контекст:** коллекция метаданных собиралась из текстового отчёта по
  конфигурации (`.txt`) символьными окнами 1500 символов. У этого подхода три
  измеренных недостатка: (1) у **78 %** таких чанков длина превышала лимит e5
  в 512 токенов — хвост текста не участвовал в эмбеддинге; (2) структура
  терялась: реквизиты, измерения, значения перечислений шли сплошным текстом;
  (3) в выборку попадали шумовые сущности (картинки, стили, роли), размывающие
  выдачу.

## Решение

Метаданные парсятся из **XML-выгрузки конфигурации** (формат «Выгрузить
конфигурацию в файлы»), а не из отчёта. Правила:

1. Один объект метаданных → одна запись `objects.jsonl` (тип, имя, синоним,
   реквизиты с типами, табличные части, измерения/ресурсы, формы, команды,
   значения перечислений).
2. Один **чанк = один объект или одно поле**: `Документ X · реквизит Y · тип: …`.
   Размер чанка по построению укладывается в лимит 512 токенов.
3. Шумовые виды (`CommonPicture`, `Style`, `StyleItem`, `Interface`, `Language`,
   `WSReference`, `XDTOPackage`, `Role`) исключаются из индекса.
4. Имена объектов и полей складываются в словарь (`data/lexicon/`) — локальный
   артефакт, используется роутером и структурными инструментами.
5. Всё строится в **отдельную коллекцию** `meta_upp11` (отдельная база), чтобы
   можно было сравнить источники и откатиться без потерь.

Скрипты: `scripts/parse_config_xml.py`, `scripts/build_metadata_index.py`,
`scripts/eval_metadata_xml.py`.

## Измерения

### A/B на одних и тех же 300 кейсах

Кейсы генерируются из самой выгрузки (структурная истина): «реквизиты
<тип> <имя>», «измерения и ресурсы регистра <имя>», «значения перечисления
<имя>», «у <тип> <имя> где хранится реквизит <поле>». Проверка — попадание
нужного имени (и поля, если спрашивали поле) в top-3; для обеих коллекций
применяется одинаковый текстовый матч, чтобы сравнение было честным.

| Источник метаданных | Чанков | BM25 Hit@3 |
|---|---|---|
| текстовый отчёт (`.txt`) | 23 808 | 93,0 % (279/300) |
| **XML-выгрузка** | 25 026 | **99,7 % (299/300)** |

Прирост **+6,7 п.п.** на идентичном наборе — это вклад структуры, а не «ощущение».

### Качество новой коллекции по типам (top-3)

| Тип кейса | Кейсов | vector | BM25 |
|---|---|---|---|
| реквизиты (attribute) | 133 | 87,2 % | **100 %** |
| значения перечислений | 40 | 100 % | 100 % |
| объекты | 85 | 45,9 % | **96,5 %** |
| регистры | 42 | 69,0 % | **95,2 %** |
| **Итого** | **300** | **74,7 %** | **98,3 %** |

Вывод: для структурированных метаданных **лексический поиск сильнее**
(точные имена), вектор полезен для перефразировок; слабое место — объектные
сводки, которые перебиваются чанками отдельных реквизитов. Следующий шаг —
гибрид BM25 + vector (RRF) по метаданным.

### Оговорки

- Векторный baseline старой коллекции восстановить не удалось: Chroma не
  сохранила векторы в sqlite (известный баг персистентности HNSW). Для строгого
  «до/после» по семантике нужен переэмбеддинг старых чанков — отдельный замер.
- Первая версия оценки давала 17,7 % — это была **ошибка методики** (запрос
  «где хранится реквизит Организация» без имени объекта; «Организация» есть у
  сотен объектов). Исправлено: имя объекта включено в запрос, объектные вопросы
  принимают любой чанк этого объекта.

## Обоснование

### Техническое

1. Устраняет обрезку 78 % чанков лимитом эмбеддера.
2. Поле = чанк: точные запросы («реквизит Инициатор», «измерения регистра X»)
   находят нужную запись, а не абзац отчёта.
3. Полнота: 5 911 объектов, 26 450 чанков до фильтрации шума, 11 850 имён в
   словаре; покрытие типов — документы, справочники, отчёты, обработки,
   регистры, перечисления, константы, формы, команды, планы.
4. A/B подтверждает прирост на одинаковых кейсах.

### Управленческое

1. **Управляемый переход:** отдельная база и коллекция, старый индекс не
   затрагивается, откат = не использовать новую коллекцию.
2. **Проверяемость:** структурная истина берётся из самой выгрузки, поэтому
   метрику нельзя «подкрутить» формулировками кейсов.
3. **Расширяемость:** словарь имён и `objects.jsonl` — основа структурных
   инструментов (`get_metadata`, `list_objects`, `list_attributes`) и точного
   распознавания имён в роутере (закрывает класс «одиночных имён» без
   расширения регексов).
4. **Конфиденциальность:** выгрузка и производные артефакты (JSONL, словарь,
   индексы) остаются локальными и не коммитятся; в публичный репозиторий
   попадают только скрипты, ADR и обезличенные метрики.

## Последствия

- Коллекция `meta_upp11` (25 026 чанков) и BM25 (`data/bm25_meta_upp11`).
- Локальные артефакты `data/metadata_xml/`, `data/lexicon/`, `data/chroma_xml/`
  в `.gitignore`.
- Следующие шаги: гибрид BM25+vector для метаданных, инструменты
  `get_metadata`/`list_objects`, использование словаря имён в роутере.
