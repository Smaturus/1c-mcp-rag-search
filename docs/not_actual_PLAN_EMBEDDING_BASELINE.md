# План: новый baseline эмбеддингов

- **Версия:** 1.6

- **Дата:** 2026-11-01

- **Статус:** модель и порядок зафиксированы. Индексация не начата. v1.5–v1.6
  добавляют preflight-гейты, стратифицированный пилот и операционные проверки до
  полной сборки. Локальный файл, в git не входит (`.git/info/exclude`).

- **Бюджет:** до 120 часов непрерывной работы на этой машине. Другие тяжёлые
  задачи на это время ставятся на паузу.

- **Машина:** Intel Core i5-12450H (8 ядер / 12 потоков), 16 ГБ ОЗУ, видеокарта
  Intel UHD. Дискретной GPU нет. Индексация и замер идут на CPU.

## Что изменено в v1.5–v1.6

- v1.6: явно пред-регистрированы два дизайн-выбора для ADR 0011: мягкое
  пилотное stop-правило (safety net, не замена парному тесту) и latency-вердикт
  по p95 полного замера, а не по пилоту.

- Корпус проверяется не только по путям и id, но и по **SHA-256 текста чанков**;
  без этого переиспользование BM25 запрещено.
- До полной сборки обязателен **стратифицированный пилот** с парным сравнением
  e5-small и e5-large на подвыборке v2 и замером throughput/RSS.
- Явно зафиксированы **ресурсные пороги** (latency, память, диск, ETA) и
  stop-условия: качество не единственный критерий.
- Добавлены `.gitignore` для артефактов large-эксперимента, проверка
  контрольной копии e5, model revision, проверка токенизации/усечения для large,
  тесты кросс-модельного скрипта, MCP/router/rollback smoke.
- Решение по модели остаётся прежним: принимается только при значимом приросте
  `hybrid` на v2 и v3; иначе baseline остаётся e5-small.

## Проверка корпуса и BM25 до сборки (обязательно)

Факты ниже уже проверены на текущем checkout:

- В `1C_Corpus` — **3444** `.bsl`; 110 файлов — BOM-only/пустые (3–9 байт).
- Сухой прогон `chunk_bsl_file(max_chars=1000, overlap=150)` по
  `sorted(rglob("*.bsl"))` дал **154 560** чанков; множество id `bsl_proc:`
  **точно совпало** с `doc_ids` в `data/bm25_all` (154 560; ключ `doc_ids`).
- В `data/chroma_xml` у code-чанков есть ключ `chroma:document` с текстом
  (проверено на 5 случайных `bsl_proc:` id) — content-hash gate выполним.
- 110 пустых файлов не дают чанков и не входят в `relevant_sources` v2/v3.
- Выборочная проверка 30 файлов: текст старых чанков совпал с новым корпусом.
  Это **не** заменяет полный content-hash gate.

Проверено по коду/базе (2026-11-01): `build_procedure_index.py` берёт
`sorted(rglob("*.bsl"))`; `--reset` делает `checkpoint.unlink()` и
`get_collection(..., reset=True)`; у обеих коллекций
`hnsw:sync_threshold=1000000`; `parse_config_xml.py` читает только `--root` и не
смотрит `MCP_1C_METADATA_XML_ROOT`; `chunk_bsl_file` детерминирован для одного
файла, а порядок файлов задаётся сортировкой до чанкинга.

Перед полной сборкой написать и запустить `scripts/check_corpus_identity.py`
(новый скрипт; входит в preflight, не в отчёт метрик). В самом начале он
проверяет на 10 случайных `bsl_proc:` id, что `chroma:document` содержит текст;
если текста нет — gate невозможен, план останавливается и пересматривается.
Далее скрипт обязан проверить:

1. Для каждого `bsl_proc:` id из `data/bm25_all/meta.json` восстановить текст
   чанка из `data/chroma_xml` (sqlite, только чтение).
2. Заново нарезать `1C_Corpus` тем же `chunk_bsl_file(max_chars=1000, overlap=150)`
   и получить те же id.
3. Сравнить **SHA-256 текста каждого чанка** старого и нового корпуса.
4. Записать манифест: SHA-256 отсортированного списка `путь + sha256 файла`,
   число чанков, SHA-256 множества текстов чанков.

Условия продолжения:

- множества id равны (иначе stop);
- **все** хеши текстов чанков равны (иначе stop);
- среди `relevant_sources` v2 и v3 нет отсутствующих `.bsl` (иначе stop);
- отчёт с манифестом сохранён рядом с отчётом замера.

Если content-hash не совпал, **нельзя** переиспользовать BM25: сравнение станет
сменой модели и корпуса. Тогда либо выравнивается корпус, либо BM25
пересобирается отдельным этапом и это фиксируется как второй фактор. Молча
продолжать нельзя.

## Факты, от которых план не отходит

Числа ниже совпадают у README, `docs/EVALUATION.md`, `docs/HISTORY.md` и отчётов
`data/eval/`.

| Набор | Что сравниваем | nDCG@10 | Парный тест `vector` − `hybrid` |
| - | - | - | :-: |
| v2 dev, 70 запросов, 4 прогона | hybrid 0.442 ± 0.012, vector 0.331 ± 0.028 | hybrid выше | Δ = −0.112, CI \[−0.184; −0.038\], p = 0.0037 |
| v3 hold-out, 71 code-запрос, 3 прогона | hybrid 0.217 ± 0.015, vector 0.208 ± 0.020 | разница в шуме | Δ = −0.0097, CI \[−0.0492; +0.0297\], p = 0.635 |

Дефолт режима — `hybrid`. Он выигрывает на v2 и не проигрывает на v3.

ADR 0009 (числа 0.339 против 0.301 и вывод «дефолт = vector») **отклонён**.
Причина того сдвига — токенизатор BM25 до CamelCase-разбиения. Действующий ADR по
этому дефекту — **0010**. Следующий свободный номер ADR — **0011**. Политику
данных под номером 0010 не заводить.

v3 — это уже 100 фраз (`gold_set_v3_holdout.jsonl`, источник `set2.txt`): 71 код,
5 метаданных, 24 вне корпуса. В nDCG кода входят 71 отвечаемый code-запрос.
Отдельного файла «100 фраз УПП» в репозитории нет. Схема v3 уже содержит
`relevant_sources`, `expected_route`, `type`, `notes`.

Порог качества тот же, что отсёк тюнинг RRF: парный t-test и bootstrap 10 000,
seed 42. Прирост есть, когда 95 % интервал не содержит 0 и p < 0.05. Сдвиг внутри
опубликованного разброса (±0.012 на v2, ±0.015 на v3) улучшением не считается.

**Primary endpoint** — `hybrid` nDCG@10; `vector` — вторичный, только для решения
о дефолте. Не выбирать модель или дефолт по post-hoc подгруппам v3; подгруппы
`type`/`category` можно показывать только как диагностику.

Абсолютные метрики скромные: e5-small не обучена на BSL, gold-set частично
синтетический. Сравниваются конфигурации на одном наборе и одном корпусе.

## Шаг 1. Зафиксировать модель, окружение и артефакты

**Зачем.** Поднять абсолютный nDCG одной сменой эмбеддинга, не смешивая её с
тюнингом поиска и не потеряв воспроизводимость.

Имя, префиксы, размерность и revision записываются до сборки. Индексация
`1C-Corpus` начинается только после этого.

| Поле | Значение |
| - | - |
| Модель | `intfloat/multilingual-e5-large` |
| Параметры / dim | 560M, 24 слоя, 1024, лимит 512 токенов |
| Префикс запроса | `query: ` |
| Префикс пассажа | `passage: ` |
| Revision | snapshot hash из локального HF-кэша; записать в отчёт |
| Источник весов | локальный кэш Hugging Face (`models--intfloat--multilingual-e5-large`) |
| Лицензия | проверить и записать (модель и веса) |
| Пакеты | версии `sentence-transformers`, `torch`, `transformers`, Python |
| Нарезка | `max_chars=1000`, `overlap=150`, id `bsl_proc:…` |
| Совместимость | те же префиксы, что у e5-small; `embeddings.py` не меняется |
| Откат | `MCP_1C_EMBEDDING_MODEL=intfloat/multilingual-e5-small`, `MCP_1C_CHROMA_DIR=data/chroma_xml` |

**Preflight-инфраструктура (до любого запуска):**

1. Остановить MCP-серверы, индексаторы и любые процессы, открывающие Chroma/BM25.
   Проверить отсутствие writer-lock. Не копировать и не строить «на живую».
2. Проверить свободное место: **до старта ≥30 ГБ**, после сборки/копии/метаданных
   ≥10 ГБ. Оценка артефактов: код 1024-dim ~0,6–1,5 ГБ с HNSW, metadata ~0,1 ГБ,
   копия `chroma_xml_eval` ~2,3 ГБ, pilot — доли ГБ; 30 ГБ — запас, не точная
   сумма. `data/chroma_e5_large` по умолчанию не удалять (историческое
   свидетельство).
3. Добавить в `.gitignore` **до** сборки:

   ```gitignore
   data/chroma_1c/
   data/chroma_xml_eval/
   data/chroma_pilot_small/
   data/chroma_pilot_large/
   data/eval/_runs_1c/
   data/eval/_pilot_1c/
   data/procedure_index_progress_1c*.json
   data/procedure_index_progress_1c_smoke.json
   data/procedure_index_progress_pilot*.json
   ```

   Текущие `data/`-артефакты не должны попасть в `git status`; проверить
   `git check-ignore` для каждого пути. Отдельно проверить, что
   `data/metadata_xml/` и `data/lexicon/` уже игнорируются (в текущем
   `.gitignore` они есть); если нет — добавить до `parse_config_xml.py`.
4. Проверить кэш модели: размер, наличие `config.json`/весов, revision; записать
   SHA-256 `config.json` и listing snapshot. Не скачивать модель заново в середине
   эксперимента.
5. Проверить токенизацию large: на стратифицированной выборке чанков посчитать
   распределение токенов токенизатором large. Если доля >512 токенов заметно
   выше текущих 0,3 % (источник: `data/eval/embedding_tokens.md`; порог: ≤1 %
   либо письменно принятый риск), зафиксировать это до сборки: иначе сравнение
   будет включать разное усечение.
6. Зафиксировать память: целевой peak RSS процесса ≤11 ГБ; 11–12 ГБ — только
   письменно принятый риск с указанием запаса; **>12 ГБ — stop**. Это RSS
   процесса индексации, не суммарная память системы; 16 ГБ ОЗУ оставляют ОС
   около 4 ГБ.

**Почему large, а не fine-tune small.** Один фактор в том же контракте
`query:` / `passage:`. На MIRACL (dev) nDCG@10: small 60.8, large 66.5; русский
язык 59.1 и 67.4 (Wang et al., 2024, arXiv:2402.05672). Дообучение small на
именах процедур усиливает сигнал, который уже несёт BM25, и на CPU без GPU не
воспроизводит батч 512.

**Успех шага.** Записаны модель, revision, префиксы, размерность, версии пакетов,
лицензия; preflight-инфраструктура пройдена. Метрик ещё нет.

**Дефолт `hybrid`.** Шаг его не меняет.

**Не трогаем.** `k = 60`, равные веса RRF, глубину каналов опубликованного
прогона, BM25 (`k1=1.5`, `b=0.75`, токенизатор ADR 0010), роутер, gold-set,
reranker, порог холодного старта HNSW.

**Переиндексация.** Нет.

**Откат.** Шаг 1 не меняет рабочий индекс; откат не требуется. Проверка —
исходные `MCP_1C_CHROMA_DIR=data/chroma_xml` и имя e5-small остаются в силе.

## Шаг 2. Пилот, затем полный индекс и парный тест v2/v3 code

### 2.1. Стратифицированный пилот (новое в v1.5)

Полную сборку на 154 560 чанков нельзя делать без раннего сигнала: smoke «поиск
отвечает» не проверяет качество и не даёт честной оценки throughput.

Пилот:

- **Выборка:** 400–500 `.bsl` файлов, стратифицированная по top-level типу
  (`Documents`, `Catalogs`, `CommonModules`, `InformationRegisters`,
  `AccumulationRegisters`, `Reports`, `DataProcessors`, `Enums`, `Constants`,
  `Charts*` и т.д.) и по размеру файла; фиксированный seed, не первые 300
  `sorted(rglob)`.
- **Запросы:** **все 70 v2-запросов** (68 уникальных relevant-файлов `bsl`).
  Оценка 70 запросов стоит секунды, поэтому мощность не теряем; v3 в пилоте не
  используется. Это go/no-go, а не приёмка.
- **Индексы:** два боковых каталога `data/chroma_pilot_small` и
  `data/chroma_pilot_large`; одна и та же коллекция `code_proc` и одни и те же
  файлы. Они не пересекаются с `data/chroma_1c` и после пилота удаляются или
  остаются как свидетельство (в git не попадают). Сравнивать large−small парно
  по nDCG@10; primary endpoint — `hybrid`, `vector` — вторичный.
- **Выбор файлов:** в подвыборку обязательно включаются все 68 relevant-файлов
  v2; стратифицированные файлы добираются до 400–500. Если gold-файлов больше
  лимита, лимит расширяется, а не запросы «подгоняются» под выборку.
  Страты: top-level тип = первый каталог после `1C_Corpus` (`Documents`,
  `Catalogs`, `CommonModules`, `InformationRegisters`, `AccumulationRegisters`,
  `Reports`, `DataProcessors`, `Enums`, `Constants`, `Charts*` и т.д.) × размер
  файла (`<1 КБ`, `1–10 КБ`, `10–100 КБ`, `>100 КБ`), фиксированный seed.
- **Batch size:** пилот измеряет throughput и peak RSS для **batch 8 и 16**;
  выбирается вариант с лучшим chunks/sec при peak RSS ≤ 11 ГБ. Этот же batch
  используется в ETA и в полной сборке; выбранное значение фиксируется в отчёте.
- **Измерения:** чанков/сек, токенов/сек, peak RSS, p50/p95 embedding latency,
  размер индекса, оценка ETA для 154 560 чанков.
- **Stop-условия (пилот — только go/no-go):**
  - верхняя граница 90 % CI для Δ (large − small) **< +0.01** — модель не даёт
    даже минимально осмысленного прироста; либо точечная Δ **≤ −0.02** — явная
    деградация;
  - ETA полной сборки × 1.1 + 8 часов замера > 120 часов;
  - peak RSS процесса > 12 ГБ (11–12 ГБ — только письменно принятый риск);
  - меньше 20 ГБ свободного диска после пилота (до старта — не меньше 30 ГБ);
  - доля >512 токенов у large >1 % без письменно принятого риска.

Пилот не является замером baseline и не отменяет парный тест на полном индексе.
Если пилот провален, полная сборка не начинается; результат фиксируется в
ADR 0011 как «остановлено на пилоте».

**Осознанный выбор (пред-регистрация для ADR 0011):** пилотное stop-правило
намеренно мягкое. При n = 70 и типичном σ ≈ 0,1 SE ≈ 0,012, 90 % CI ≈ ±0,02;
порог «upper 90 % CI < +0.01» срабатывает в основном при point Δ < −0.01.
При истинном Δ = 0 вероятность stop ≈ 20 %, при Δ = +0.02 — ≈0,6 %, при
Δ = −0.02 — ≈80 %. Это защищает от ложного стопа хорошей модели, но при
плоском результате **допускает** полную сборку: пилот — safety net, а не замена
парному тесту на полном индексе. Это принято как цена защиты от false stop и
должно быть записано в ADR 0011. Более строгий второй триггер в v1.5 не
включается.

### 2.2. Полная сборка

1. Повторить content-hash гейт из раздела «Проверка корпуса и BM25».
2. Запустить `scripts/build_procedure_index.py`:
   - `MCP_1C_STUDY_ROOT=D:\MCP_1С_homework\1C-Corpus\1C_Corpus`
   - `MCP_1C_EMBEDDING_MODEL=intfloat/multilingual-e5-large`
   - `MCP_1C_CHROMA_DIR=data/chroma_1c`
   - `--reset` только в `data/chroma_1c`
   - порядок файлов — `sorted(rglob("*.bsl"))`, не перемешивать;
   - `max_chars=1000`, `overlap=150`, id `bsl_proc:…`
   - batch size — **выбранный в пилоте** (8 или 16), зафиксировать в отчёте;
   - один писатель, без параллельной индексации;
   - перед запуском удалить `data/procedure_index_progress_1c.json`.
3. В процессе писать в лог: файлы/чанки, chunks/s, ETA, RSS, температуру/троттлинг
   (если доступно), свободное место. Каждые **50 файлов** обновлять checkpoint.
   Если sustained chunks/s падает более чем на 20 % от пилота — пересчитать ETA;
   при выходе за бюджет остановиться и записать это в ADR 0011.
4. При прерывании: не начинать замер; проверить checkpoint, продолжить с него или
   пересобрать; факт прерывания — в отчёт/ADR.

### 2.3. Post-build gates (до любого замера)

- `code_proc` содержит **154 560** чанков (или ровно то число, что дал
  content-hash preflight; расхождение — stop).
- Все `source` оканчиваются на `.bsl`; `.xml` нет; пути — под `1C_Corpus`.
- Множество id `bsl_proc:` равно множеству `doc_ids` BM25 (154 560).
- **SHA-256 текста каждого чанка** совпадает с preflight-манифестом; иначе stop.
- Размерность каждого вектора — 1024; проверить случайную выборку **1000 id**
  (не только первый).
- `relevant_sources` v2/v3 code присутствуют в индексе.
- Короткий поисковый smoke: 5 запросов, top-10, `vector` и `hybrid` отвечают;
  smoke не входит в метрики. Это smoke бокового индекса, без переключения MCP;
  полный MCP/9 tools — только в 3.3.

### 2.4. Контроль e5 и протокол замера

Парный тест снимается только с полного индекса и после всех gates.

**Контроль e5:**

- остановить все процессы, которые могут открывать `data/chroma_xml`;
- скопировать базу в `data/chroma_xml_eval` (лучше остановить writer, затем
  `Copy-Item -Recurse`; при возможности — sqlite backup, а не копирование WAL
  «на живую»);
- после копии проверить: `PRAGMA integrity_check`, counts `code_proc` = 154 560,
  `metadata_xml` = 25 026, размерность вектора = 384, пробный запрос;
- исходный `data/chroma_xml` не открывать на запись и не изменять.

**Замер:**

- отчёты в `data/eval/_runs_1c`; опубликованные `data/eval/code_proc` и
  `data/eval/v3_code` не перезаписывать;
- каждый процесс — новый;
- v2: 4 процесса, 70 запросов; v3 code: 3 процесса, 71 запрос;
- large и e5 — на одних и тех же запросах и с одинаковым протоколом;
- `search(..., top_k=10)`; глубину каналов не менять (50 откатили);
- `eval_pipeline.py` затирает `report_pipeline.json`, поэтому сразу копировать
  его под устойчивым именем `v2_e5_hybrid_run1.json` и т.д.; если целевой файл
  уже существует — **fail/новый run id**, не молча перезаписывать;
- в отчёт: SHA-256 gold-set, model revision, версии пакетов, каталог, число
  чанков, token stats, peak RSS, p50/p95 latency, дата, manifest корпуса.

### 2.5. Кросс-модельный paired-скрипт

Скрипта пока нет; он пишется и тестируется **до** полной сборки, не во время
индексации.

Контракт:

- вход — файлы одного режима и одной модели; per-query `ndcg@10` усредняется по
  прогонам;
- соединение e5 и large по `id`; если множества id не равны — stop;
- Δ = large − e5; bootstrap 10 000, seed 42; paired t-test;
- вывод: средние, Δ, CI, p, wins/ties/losses, n;
- unit-тесты на синтетике: одинаковые id, разные длины, отсутствующий id,
  нулевая дисперсия, перестановка порядка.

Без тестов скрипта замер не считается валидным.

### 2.6. Успех шага 2

**Качество:**

- на v2 средний nDCG@10 `hybrid` выше 0.442 и парный тест против e5 значим
  (CI > 0, p < 0.05);
- на v3 — значимый прирост `hybrid` против 0.217 на 71 code-запросе;
- выигрыш только на v2 при плоском v3 не делает модель новым baseline.

**Ресурсы (новое в v1.5, проверяется до принятия):**

- p95 latency `hybrid` на large ≤ 2× p95 e5-small на той же машине. Абсолютный
  порог из пилота — только ориентир; финальное решение по latency принимается по
  p95 **полного замера** в §2.4, а не по пилоту на 400–500 файлах (пилот не
  воспроизводит размер HNSW-графа и холодный старт полного индекса);
- peak RSS ≤ 12 ГБ;
- ETA полной сборки уложилась в бюджет с 10 % резервом (см. формулу ниже);
- после сборки и копии свободно ≥10 ГБ;
- side-index smoke: `search`/`search_hybrid` на `data/chroma_1c` отвечают;
  полный MCP smoke с 9 tools — только в 3.3.

Если качество выросло, а ресурсный порог нарушен — модель не принимается;
результат фиксируется как «качество лучше, эксплуатационно неприемлемо».

**Дефолт `hybrid`.** Замер его не переключает. Для шага 3 на новом индексе
считается парный `vector` против `hybrid`: на v2 hybrid значимо лучше vector, на
v3 — не значимо хуже.

**Не трогаем.** Всё из шага 1, `metadata_xml` до решения, `MCP_1C_SEARCH_MODE`,
RRF/BM25/нарезку. v3 не используется, чтобы выбрать вторую модель или подкрутить
RRF. Набор уже открыт; подстройка по нему в эту итерацию запрещена.

**Переиндексация.** Полный `code_proc` корпуса `1C-Corpus` в `data/chroma_1c`.
`data/chroma_xml`, `data/chroma_e5_large` и рабочий BM25 не изменяются.

**Откат.** Процесс снова смотрит на `data/chroma_xml` и e5-small.

## Шаг 3. Принять модель, проверить metadata/MCP/router и оставить e5 или переключиться

### 3.1. Решение по модели

**Модель принимается** только если шаг 2 успешен и по качеству, и по ресурсам,
на v2 и v3. Иначе baseline остаётся e5-small.

**Дефолт `hybrid` меняется** только в одной клетке: на новом индексе hybrid
значимо хуже vector на v2 или на v3. Тогда дефолтом становится vector. В
остальных клетках дефолт остаётся hybrid, принята модель или нет. Подстраивать
RRF под новую модель в этом шаге нельзя.

### 3.2. Метаданные (только при принятии)

Перед переключением metadata пересобираются, а не дописываются: запрос large не
должен попасть в коллекцию другой размерности.

- Коллекция: `metadata_xml` в `data/chroma_1c`.
- `scripts/parse_config_xml.py --root D:\MCP_1С_homework\1C-Corpus\1C_Corpus`;
  `MCP_1C_METADATA_XML_ROOT` он не смотрит. Пишет `data/metadata_xml/objects.jsonl`,
  `chunks.jsonl`, `stats.json`, `data/lexicon/names.json`.
- Затем `scripts/build_metadata_index.py --reset` с
  `MCP_1C_EMBEDDING_MODEL=intfloat/multilingual-e5-large`,
  `MCP_1C_CHROMA_DIR=data/chroma_1c`.
- До `--reset` — список коллекций и длина вектора; после — длина 1024 у всех
  проверенных векторов, count > 0. Иначе stop.
- После сборки: 5 metadata-запросов v3 (индикативно) + проверка, что
  `index_stats` видит обе коллекции; `data/lexicon/names.json` содержит те же
  ключи, что до пересборки (diff пустой); router — порог из 3.3.
- Metadata A/B 99,7 % — измерение до ADR 0010; не использовать как текущую
  цифру без перезамера, только как исторический ориентир.

Если на metadata не остаётся времени внутри 120 часов, глобальная модель не
переключается: боковой индекс кода сохраняется как результат замера, рабочий
контур остаётся на e5.

### 3.3. MCP, router и откат

- MCP stdio smoke: 9 tools, `index_stats`, `search`, `search_hybrid`,
  `route_query`; проверить, что нет смешения 384/1024.
- Router regression 68/68 на dev: **не ниже 66/68** (допускается падение не более
  2 кейсов); v3 router 58/100 — только отчёт, не гейт. Ниже 66/68 — stop и
  разбор, почему смена эмбеддинга меняет роутер.
- Rollback smoke: вернуть `MCP_1C_CHROMA_DIR=data/chroma_xml` и
  `MCP_1C_EMBEDDING_MODEL=intfloat/multilingual-e5-small`, перезапустить процесс,
  выполнить 3 запроса и `index_stats`; только после этого считать откат готовым.
- `data/chroma_xml` к моменту отката не изменён.

### 3.4. ADR 0011

Один ADR с одним из исходов:

1. принято и переключено;
2. отклонено по качеству;
3. качество лучше, но нарушены ресурсные пороги — не переключено;
4. остановлено на content-hash/preflight;
5. остановлено на пилоте;
6. принято по v2/v3 code, но metadata не собраны в остатке бюджета — не
   переключено;
7. провал post-build gate id/текстов — индекс оставлен, модель не сравнивалась.

ADR 0011 обязан явно зафиксировать оба дизайн-выбора: (а) пилотное stop-правило
мягкое, при плоском пилоте полная сборка допускается — это цена защиты от false
stop, а не доказательство качества; (б) latency-вердикт принимается по p95
полного замера, пилотный абсолютный порог — только ориентир.

Чекпоинт чужой модели в git не коммитится. При отказе боковой каталог можно
удалить; `data/chroma_xml` к этому моменту не изменён.

## Бюджет 120 часов

| Работа | Внутри бюджета |
| - | - |
| Preflight: хеши, gitignore, копия, revision, токенизация | да, 2–4 часа |
| Пилот: 400–500 файлов, e5-small + e5-large, 70 запросов | да, 2–4 часа |
| Полная сборка `code_proc` по `1C-Corpus` в `data/chroma_1c` | да, ETA_build × 1.1 + 8 ч ≤ 120 |
| Контрольные e5 (4 + 3 процесса) и large (4 + 3) | да, 8 часов |
| Пересборка `metadata_xml` | только если модель принята и время осталось |
| MCP/router/rollback smoke | да, ≤1 часа |
| Вторая модель, ablation, fine-tune, ручная разметка | нет |

Сборка не начинается, если **ETA_build × 1.1 + 8 часов > 120 часов**, где
ETA_build — оценка полной сборки 154 560 чанков по throughput пилота на выбранном
batch size. Восемь часов на замер — резерв, а не оценка; 14 процессов по 60–70 с
на HNSW и ~986 запросов укладываются в него с запасом.

## Что в эти 120 часов не входит

- **Fine-tune e5-small** на синтетике: нет GPU и это отдельная итерация.
- **Новый gold-set на 100 фраз и валидатор**: проверочные наборы уже есть.
- **Порог «+5 % / −2 %»**: он принимает шум; решение принимает парный тест.
- **Смена дефолта на vector по ADR 0009**: ADR отклонён.
- **`hybrid_rerank`/`pearson` как кандидаты в дефолт**: оба отклонены.
- **Повторный 2×2 «выгрузка × нарезка»**: дамп утрачен, вывод не меняет дефолт.
- **Новый hold-out роутера**: нужен только для заявления о приросте; такого
  заявления нет.
- **Английский README, смена чанкинга, веса RRF, глубина каналов 20–50,
  холодный старт HNSW, инкрементальный индекс, корпус БСП.**

## Если модель не даст прироста

ADR 0011 фиксирует исход — не только «отклонено по качеству», но и остановку на
preflight/content-hash, пилоте, ресурсных порогах, post-build gate или
недостатке времени на metadata (исходы 3–7 в 3.4). Во всех этих случаях
рабочий контур остаётся e5-small и `hybrid`, а следующий шаг выбирается заново и
в эти 120 часов не стартует. Допустимые продолжения, каждое отдельным планом и
одним фактором: другая заранее названная готовая модель на тех же v2 и v3 либо
отдельный план обучения на парах, которые не являются парафразами v2 и v3.
Вторую модель по ошибкам уже открытого v3 не подбирать.
