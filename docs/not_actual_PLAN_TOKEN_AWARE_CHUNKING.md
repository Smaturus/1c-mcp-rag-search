# План: token-aware нарезка и пересборка baseline e5-small

- **Версия:** 1.3
- **Дата:** 2026-11-01
- **Статус:** план открыт. Индексация не начата. Локальный файл, в git не входит.
- **Бюджет:** до 38 часов работы на этой машине (без GPU): 28 ч фиксированных
  upper-оценок + до 8 ч на `ETA_build × 1.1` + 2 ч резерв. Stop-формула
  учитывает preflight, chunker, pilot, отчёты и оба замера.
- **Машина:** Intel Core i5-12450H (8 ядер / 12 потоков), 16 ГБ ОЗУ, Intel UHD.
- **Связь с предыдущим планом:** `docs/PLAN_EMBEDDING_BASELINE.md` v1.6 остановлен на
  preflight-гейте 0.7. Причина — не e5-large, а текущая нарезка: 14,43 % чанков
  длиннее 512 токенов XLM-R. Текущий индекс e5-small уже усекает эти чанки.

## Что изменено в v1.2–v1.3

- v1.3: убран двойной учёт времени сборки в бюджетной таблице; SHA-условие
  операционализировано; частичный старый набор считается отсутствующим;
  зафиксированы cleanup копии, прямое чтение BM25, smoke-запрос, metadata-разница
  old/new eval и лицензия e5-small.
- A2: stop-формула учитывает **все** фазы: preflight + chunker + pilot +
  старый контроль + новый замер + отчёты + резерв; одной `ETA_build` недостаточно.
- A1: старый baseline переснимается 4+3 прогона; сравнение old-vs-new парное.
  Переиспользование старых ранов разрешено только при совпадении gold-set SHA,
  commit SHA и model revision.
- A3: зафиксировано, что v2 — 70 code-запросов без metadata.
- Риск Chroma: старый контроль идёт **с копии** `data/chroma_xml_eval`, а не с
  живого `data/chroma_xml`; после копии — integrity/counts/dim checks.
- B1–B5 и C: оценка роста чанков, точный token budget, пересчёт аудита с
  префиксами, stop-формула с paired, вторая итерация вне бюджета; уточнены
  min_tokens/max_chars/coverage, checkpoint, batch, троттлинг, прерывание,
  ADR 0011/0012, пути pilot-корпуса.

## Зачем этот план

Аудит (`data/local_notes/embedding_baseline/audit/audit.md`) показал:

- 22 308 из 154 560 code-чанков (14,4332 %) длиннее 512 токенов;
- p50 369, p95 580, p99 601, max 793;
- e5-small и e5-large используют один XLM-R-токенизатор с лимитом 512;
- значит, усечение — свойство нарезки `max_chars=1000`, а не выбранной модели;
- «0,3 %» в старом плане — артефакт 800-файлового smoke и другого корпуса;
  `data/eval/embedding_tokens.md` — это **32,1 %** на старом чанкинге 124 253
  чанка, его нельзя использовать как текущую цифру.
- опубликованные 0.442 (v2) и 0.217 (v3) уже сняты с этим усечением.

Цель: убрать усечение, пересобрать **e5-small** на token-aware чанкинге и измерить,
не ухудшилось ли качество. Модель large в этом плане не проверяется: сначала нужен
чистый baseline на новой нарезке.

## Что не входит

- Смена модели, e5-large, fine-tune, reranker, RRF, router, metadata, дефолт
  `MCP_1C_SEARCH_MODE`.
- Новый gold-set; используются v2 и v3 как есть.
- Перезапись опубликованных `data/chroma_xml`, `data/bm25_all`, `data/eval/code_proc`,
  `data/eval/v3_code`.
- Обновление README/ADR до решения (после решения — отдельная команда).

## Корпус и исходные данные

- `1C-Corpus/1C_Corpus`: 3444 `.bsl`, 110 BOM-only/пустых, 154 560 чанков при старом
  чанкинге `max_chars=1000`, `overlap=150`.
- Gold-set v2: 70 запросов, **все 70 — code с `.bsl` relevant-файлами**;
  metadata-запросов в v2 нет (проверено по `gold_set_v2.jsonl`). v3 в этом плане —
  только 71 code-запрос; 5 metadata-запросов v3 не участвуют.
- Контрольный старый индекс: `data/chroma_xml` (read-only), старый BM25:
  `data/bm25_all` (read-only).
- Токенизатор: XLM-R от `intfloat/multilingual-e5-small`; лимит модели 512
  (`max_seq_length`). Новый chunker обязан считать токены **тем же** токенизатором
  и включать всё, что реально уходит в модель: `passage: `, префикс
  `// file… · proc…`, служебные токены `</s>` и т.п.

## Ключевое решение по нарезке

Сделать **token-aware chunker**, а не менять `max_chars` вслепую.

Требования:

1. Резать по границам `Процедура`/`Функция` … `КонецПроцедуры`/`КонецФункции`.
2. Бюджет считать строго по тексту, который получает модель:
   `len(tokenizer("passage: " + prefix + body, add_special_tokens=True,
   truncation=False).input_ids) <= 500`. 500 — это уже с префиксом и
   спецтокенами; 12 токенов до 512 — страховка на случай, если `embed_passages`
   добавит нормализацию/доп. спецтокен. Если префикс сам длиннее 500 — ошибка,
   а не повод обрезать путь. В отчёте зафиксировать формулу и tokenizer revision.
3. Целевой размер — 450–500 токенов; overlap — 50–80 токенов, не по символам.
4. Длинную процедуру резать по строкам/блокам, а не посередине идентификатора.
   Если одна строка/токен-блок не влезает — резать по токенам с overlap.
5. Префикс `// file… · proc…` входит в бюджет каждого чанка; если сам префикс
   длиннее бюджета — это ошибка, а не повод обрезать путь.
6. `max_chars=2000` — только аварийный предел: если текст длиннее, сначала
   резать по строкам/токенам; не полагаться на символы как на основной критерий.
7. Хвост короче `min_tokens=32`: если `prev_tokens + tail_tokens <= 500` —
   приклеить к предыдущему; иначе оставить отдельным непустым чанком. Непустой
   остаток не выбрасывать; политика 500 не должна нарушаться склейкой.
8. Код вне процедур — отдельный module-header чанк; пустые/пробельные файлы
   пропускаются; `chunk_index` детерминирован.
9. ID чанка — как раньше: `bsl_proc:<sha1(source)[:16]>:<chunk_index>`; новые
   индексы и ID не обязаны совпадать со старыми — BM25 будет пересобран.
10. Реализация — новый модуль/функция, например `chunk_bsl_file_tokens`, и
    отдельный флаг/скрипт сборки. Старую `chunk_bsl_file` не менять, чтобы
    сохранить воспроизводимость старых отчётов.

### 1. Реализация и тесты chunker

1. Добавить token-aware chunker с параметрами:
   - `max_tokens=500`, `overlap_tokens=64`, `min_tokens=32` (последний чанк может быть
     короче);
   - `max_chars` остаётся только как защитный предел, но не как основной критерий.
2. Считать токены ровно так, как их увидит `mcp_1c_rag.embeddings.embed_passages`
   (проверить по коду: какие префиксы/нормализация добавляются); проверить, что
   `len(tokenizer(text, truncation=False, add_special_tokens=True).input_ids) <= 512`
   для каждого чанка, включая `passage: ` и спецтокены.
3. Тесты (unit, без индексации):
   - синтетическая длинная процедура на кириллице/CamelCase: нет чанков >500;
   - overlap присутствует, но не дублирует весь чанк;
   - границы процедур не теряются;
   - пустой файл/BOM-only → 0 чанков;
   - одинаковый вход → одинаковые ID (детерминизм);
   - source/`chunk_index` уникальны;
   - префикс учитывается в бюджете;
   - файл с одной строкой >500 токенов корректно режется.
4. Прогнать chunker на полном `1C_Corpus` **без эмбеддингов** (только токенизация):
   - 0 чанков >512;
   - 0 чанков с пустым текстом;
   - покрытие непустых байтов кода ≥99,6 %; **100 % непустых файлов** должны дать
     хотя бы один чанк; если 0,4 % не покрыты — объяснить, что это (пробелы/служебные
     вставки), а не молча принять;
   - распределение токенов: p50/p95/p99/max;
   - число чанков и суммарное время.
   Если >512 есть — исправить chunker, не запускать сборку.

### 2. Пилот сборки e5-small

1. Выбрать 300–500 файлов стратифицированно: top-level тип × размер
   (`<1 КБ`, `1–10 КБ`, `10–100 КБ`, `>100 КБ`), фиксированный seed; включить
   файлы с самыми длинными процедурами. Скопировать их с сохранением путей в
   `data/token_pilot_corpus` (этот каталог только для pilot, в git не входит).
2. Собрать pilot-индекс `data/chroma_token_pilot` на e5-small, `max_tokens=500`,
   `overlap_tokens=64`; отдельный checkpoint
   `data/procedure_index_progress_token_pilot.json`; `--reset` только в pilot.
3. Замерить: elapsed, chunks, chunks/sec, peak RSS, ETA для полного корпуса.
   Batch size: измерить 8 и 16, выбрать лучший chunks/sec при peak RSS ≤ 11 ГБ;
   этот же batch идёт в ETA и полную сборку.
4. Stop-условия:
   - бюджетная формула (см. §5): `elapsed(preflight+chunker+pilot) +
     ETA_build × 1.1 + old_control_remaining + 8 (new eval) +
     reports_upper(2) + reserve(2) > 38` → STOP. Если старый контроль
     переиспользуется, `old_control_remaining = 0`, иначе 8;
   - peak RSS > 12 ГБ (11–12 ГБ — только письменный риск);
   - <15 ГБ свободно после pilot;
   - появились чанки >512.
5. Если пилот не прошёл — STOP, полную сборку не запускать.

### 3. Полная сборка e5-small и BM25

1. Собрать `data/chroma_token` на e5-small, `max_tokens=500`, `overlap_tokens=64`,
   тем же chunker; batch size — выбранный в пилоте (8 или 16); зафиксировать.
   - checkpoint каждые **50 файлов**; отдельный путь
     `data/procedure_index_progress_token.json`;
   - в лог: files, chunks, chunks/s, ETA, peak RSS, свободное место,
     температура/троттлинг (если доступно);
   - при падении sustained chunks/s >20 % от пилота — пересчитать ETA; при
     выходе за 38 ч — остановиться;
   - при прерывании: проверить checkpoint; либо продолжить с него, либо
     пересобрать; факт записать в отчёт. Не начинать замер на неполном индексе.
2. Post-build gates:
   - все чанки **≤500 токенов** (политика) и отдельно **≤512** как sanity против
     расхождения с `embed_passages`; полный перебор, не выборка;
   - vector dim = 384;
   - все source — `.bsl`, под `1C_Corpus`;
   - все `relevant_sources` v2/v3 code присутствуют;
   - нет пустых чанков;
   - 0 XML-путей;
   - короткий поисковый smoke: `vector`/`hybrid` отвечают.
3. Собрать `data/bm25_token` из нового `data/chroma_token`:
   `python scripts/build_bm25.py --chroma-dir data/chroma_token --out data/bm25_token`.
4. Проверить, что множество id в новом Chroma == `doc_ids` нового BM25;
   старый BM25 не переиспользовать.

### 5. Решение

**Бюджетная формула (обязательна до старта полной сборки):**

`elapsed_actual(preflight + chunker + pilot) + ETA_build × 1.1 +
old_control_remaining + 8 (new eval) + reports_upper(2) + reserve(2) <= 38`.

`old_control_remaining = 8`, если старый контроль переснимается; `0`, если
найден валидный старый 4-прогонный набор. При worst-case фиксированных 28 ч
(2+6+2+8+8+2) и резерве 2 ч на сборку остаётся 8 ч, то есть `ETA_build <= 7,3 ч`
при пересъёмке старого контроля; если старый контроль найден — `ETA_build <= 14,5 ч`.
Если формула не выполнена — STOP до полной сборки.

**Chunking принимается**, если:

- 0 чанков >512 токенов;
- покрытие и source-gates пройдены;
- на v2 `hybrid` **не хуже** старого baseline в пределах non-inferiority margin
  −0.01 (95 % CI lower bound > −0.01) — улучшение приветствуется, но не требуется
  для принятия chunking;
- на v3 нет значимой деградации: 95 % CI lower bound > −0.015; v3 — только
  подтверждение, не тюнинг.

Если качество значимо упало — chunking не принимается; ADR 0011 фиксирует
отрицательный результат. Повторная chunking-итерация (другие `max_tokens`,
overlap, границы split) — **отдельный план и отдельный бюджет**, в эти 38 ч не
входит. Модель не менять.

Если chunking принят:

- это новый baseline нарезки для e5-small;
- старый `data/chroma_xml`/`data/bm25_all` остаются как исторические;
- следующим отдельным планом будет e5-large **на этой же новой нарезке**;
- ADR 0011: token-aware chunking (accepted/rejected по итогам); embedding-план
  v1.6 остаётся остановленным и при возобновлении получает **ADR 0012**.

## Откат

Рабочий контур не переключается в этом плане. Новые артефакты — только
`data/chroma_token`, `data/bm25_token`, `data/eval/_runs_token`. При отказе они
удаляются; `data/chroma_xml`, `data/bm25_all`, `MCP_1C_CHROMA_DIR`,
`MCP_1C_EMBEDDING_MODEL` не меняются.

| Новый замер v2/v3 | 8 ч |
| Отчёты + ADR | 1–2 ч |
| **Фиксированные upper-оценки без сборки** | **28 ч** (20 ч, если old control найден) |
| **Резерв** | **2 ч** |
| **Бюджет** | **38 ч** |

Если старый контроль найден и валиден, фиксированные upper-оценки — 20 ч, и на
сборку остаётся 16 ч (`old_control_remaining = 0`); это разрешено только при
выполнении всех SHA-условий из §4.1.

Для уже завершённых фаз в формуле используется **факт** (`elapsed_actual`), для
предстоящих — **upper-оценка**; таблица даёт верхнюю границу до старта. Формула
stopping: `elapsed_actual(preflight+chunker+pilot) + ETA_build × 1.1 +
old_control_remaining + 8 + reports_upper(2) + reserve(2) <= 38`. Если она не
выполнена — STOP до полной сборки.

## Если chunking не помогает

Записать отрицательный результат; текущий baseline остаётся e5-small на старой
нарезке; large не запускать. Следующие варианты — отдельными планами: другой
token budget/overlap, token-aware split по AST/блокам, код-ориентированная модель
или long-context модель. Не смешивать несколько факторов в одной итерации.
